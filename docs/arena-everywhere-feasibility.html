Architecture audit · 2 November 2026

Arena Everywhere

One shared ecosystem, native device shells, and explicit execution limits.

Conclusion: The vision is feasible as a shared data/service platform with small native console applications—not as an Electron or React application copied onto consoles. Reuse existing Arena contracts and services. Build one native shell first, prove actual launching and recovery, then expand.

Scope: an architectural survey of the current working tree and primary SDK documentation. This is not an exhaustive historical-branch reconciliation or an end-to-end certification of existing rooms. No application code, dependencies, firmware, game files or runtime registrations were changed for this report.

2. Ten concrete gaps before claiming portability

  1. The canonical game contract is frontend-owned. Core concepts and compatibility functions currently live alongside browser code. Some manifest construction also emits browser-specific save locations. Extract only the neutral contract/checks; retain environment-specific construction and persistence in adapters.
  2. OS/platform compatibility is not explicitly compared. ArcadeHost contains platform, but the inspected runtime check compares host kind, CPU architecture, runtime version and capability flags—not that platform field. Console adapters need explicit OS/ABI/environment requirements. “ARM64” alone cannot distinguish Switch Horizon, Android and Linux.
  3. Native projection is hard-coded to Windows. Its runtime ID, isolation requirement, permission descriptions and AppContainer save locations are Windows-specific. A generic-looking descriptor must not produce Windows claims for another device.
  4. There is no portable storage/sync interface in the surveyed paths. IndexedDB and desktop-private paths are implementation details, not console locations. A console needs local SD storage and recovery without a running Node/PostgreSQL host.
  5. Device enrollment is not yet a console pairing flow. Existing identity code is useful authority, but the console UI, credential provisioning, trust level, renewal and revocation behavior need explicit design and tests.
  6. Runtime evidence needs device-environment specificity. Existing evidence is tied to host, content, runtime version and profile. New console records must also make firmware/loader environment and the tested execution mode identifiable; availability is not gameplay proof.
  7. Save portability is not automatic. A common title or even matching source repository does not establish matching save format. Emulator states, SRAM, native saves and configuration need separate compatibility declarations and explicit copy/restore—not silent identity merging.
  8. Mod manifests are not console installation adapters. Base hashes/dependency checks can be shared; device filesystem mappings, installed-title identity, patch application and power-loss recovery need native implementations. Windows BepInEx DLLs are not portable console plugins.
  9. Desktop isolation claims cannot be carried over. Separate folders and permission declarations do not establish an enforced console sandbox. Arena has not implemented or proven such enforcement on these targets. Community native code must be treated according to its actual privileges.
  10. No console toolchain or shell has been demonstrated here. The targeted source scan found no libctru/libnx/libogc integration or console executable packaging. No target cross compiler was found on PATH. No console build, emulator run or hardware test was performed.

Core is a contract and authority boundary, not one universal executable

  • Keep existing TypeScript services authoritative where they already work. Extract neutral types, schemas and pure compatibility policy into a shared package without changing existing callers or save identities.
  • Publish a versioned, bounded wire format with shared validation/conformance fixtures. Native consoles cannot import a TypeScript package merely because its types are platform-neutral.
  • Implement only the necessary offline subset in a small shared C/C++ library used by all console shells. Keep SDK calls behind storage, input, display, clock, network and launch interfaces. This is one common native implementation—not three independent catalog/mod systems.
  • Use the same fixtures to check native and existing service behavior. A shared JSON schema alone does not guarantee matching business rules.
  • Do not move the current whole manifest module blindly: browser save-location construction belongs outside the neutral contract. Preserve existing URLs, metadata schemas and private ownership during extraction; introduce versioned migrations rather than destructive replacement.

Offline storage and synchronization

Local catalog, settings, approved installed content and launch recovery must work with networking disabled. Use bounded indexes and lazy artwork decoding, not a full desktop database or an eager artwork collection in RAM. Determine memory budgets from each SDK baseline and measure them on the target; this audit provides no fabricated performance figures.

For SD/FAT storage, design recoverable generations or dual-slot records with hashes and sequence numbers. Stage new payloads before committing a pointer; retain the last valid generation. Do not assume desktop transactional guarantees or that a rename alone proves power-loss durability. Test interrupted writes and low storage.

Synchronize three distinct categories: portable metadata (collections/preferences), explicitly transferable user files (declared compatible saves/artwork), and platform-specific executables/mod outputs (only for matching adapters). Conflicts preserve both versions and require resolution where progress could be lost. A disconnected console remains useful; pending remote AI jobs must not block local play or silently execute destructive actions after reconnection.

Which one first?

Provisional recommendation: Wii. A small offline launcher offers a clear first vertical slice without dual-screen or handheld/docked complexity. This is a recommendation based on the inspected SDK/packaging paths, not proof that its handoff implementation is already solved. Hardware availability is unknown. If the available test device is a 3DS or Switch, choose that instead rather than building an untestable first port.

5. Arcade, Modder, extensions and agents

  • Arcade: Keep one library identity/provenance model. Each platform registers only actual native ports, emulator adapters or homebrew executors with matching prerequisites. An open-source catalog entry is discovery metadata, not an executable for every device.
  • Emulators: Assess each target build, core, content format, controls, performance and license separately. Browser EmulatorJS assets and desktop DOS/Windows executors do not establish a console implementation. Save-state portability must be declared by exact core/version/format, not inferred.
  • Universal Modder: Begin with one reviewed data-patch adapter on one lawful game/port. Reuse base/version/dependency/hash semantics and keep original files recoverable. Console-specific overlays, title identifiers and runtime patchers require separate assessments; none is claimed integrated here.
  • Community extensions: Separate data packages (themes, metadata, controller profiles) from executable packages. Bound sizes, validate paths and dependencies, verify hashes and record provenance/licenses. Signature verification identifies a publisher; it does not make native code safe. No automatic native-code execution.
  • Agents: Existing missions remain on an appropriately capable host. A future console UI may submit fixed, scoped requests and show approvals, progress and results. Do not give it a raw terminal/tool-proxy endpoint or claim an offline Wii hosts the current Linux workspace/browser automation stack.

6. Delivery sequence and acceptance gates

  1. Contract extraction: Isolate existing game/runtime/mod DTOs and pure policy; add explicit platform/ABI requirements. Keep old browser/native consumers working. Test unknown runtimes, wrong OS with matching CPU, wrong version, missing capabilities and old schema handling.
  2. One SDK build probe: Select one target and use official toolchain distributions. Record exact compiler, SDK/library versions and artifact hashes. Build a minimal native program before adding application logic. Do not install all three SDKs or bundle them in the Windows app. Toolchain setup has not been verified in this workspace.
  3. Native offline shell: Load a bounded exported catalog from local storage; navigate with actual controls; persist settings and one declarative theme. Display unsupported entries honestly. Cold start must succeed without the companion host.
  4. Real game handoff: Launch one authorized homebrew game or open-source native port. Confirm visible gameplay and input, then demonstrate the supported return/relaunch path. Test missing/corrupt executables and an interrupted launch journal.
  5. One real mod path: Show a visible change to that compatible game/port, then disable, update, fail an incompatible update, repair and roll back without losing newer saves. File copies or synthetic logs alone do not pass.
  6. Scoped pairing/sync: Reuse existing owner/device authority. Start with metadata, then explicitly compatible file transfers. Prove offline edits, reconnect conflicts, revocation and interrupted transfers before broadening permissions.
  7. Second device: Link the same shared native subset and implement only new SDK adapters/shell presentation. Shared conformance fixtures must pass unchanged before claiming the ecosystem is genuinely reused.

Native CI can establish reproducible compilation and run host-side policy/recovery tests. Emulator tests can add evidence for specific behavior; they are not universal substitutes for actual controls, storage timing, firmware/loader mode or power-loss tests on hardware. No Windows test is required merely to conduct this audit.
